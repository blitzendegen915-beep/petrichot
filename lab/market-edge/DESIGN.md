# market-edge — 取引所間の「歪み」が本当に取れるのかを、自分のデータで確かめる実験

**発注コードは含まない。** これは儲けるためのbotではなく、「儲かる歪みが実在するか」を金銭リスクゼロで測定するための計測装置。

---

## 0. 結論から

作れる。ただし作るべきものは「歪みを見つけて執行するbot」ではなく、**記録装置と、その記録に対する再生・検算エンジン**の2つ。

理由は単純で、この実験で知りたいことが「歪みはあるか」ではなく「**手数料とレイテンシと送金コストを引いた後も残るか**」だから。前者は接続すれば5分でわかる。後者は記録してから後で答え合わせしないと絶対にわからない。そして後者が全部。

したがって設計の中心はここになる:

> **ライブのプロセスは記録しかしない。判定は後からログを再生して行う。**

これを分ける利点が大きい:

| | ライブで判定する設計 | 記録と判定を分ける設計 |
|---|---|---|
| 判定ロジックのバグ | データごと失われる | ログは無事。直して再実行 |
| パラメータ変更 | 翌日まで待つ | 同じ日を何度でも再計算 |
| レイテンシ想定を変える | 不可能 | Δ=0/100/300ms/1s を並べて比較できる |
| 再現性 | なし | 完全に決定的 |

Δ(想定レイテンシ)を振って結果がどう崩れるかを見るのが、この実験の一番の収穫。ライブ判定型だとそれが**構造的に不可能**になる。ここは譲らないほうがいい。

## 1. 対象取引所

国内の登録業者のみ。かつ、素のJSON over WebSocketで喋れるところに絞る(Socket.IOを使う取引所は依存が増えるので初版では外す)。

| 取引所 | 板の配信 | 備考 |
|---|---|---|
| bitFlyer | JSON-RPC 2.0 over WebSocket | snapshot + 差分。板は`lightning_board_*`系 |
| GMOコイン | 素のJSON WebSocket | `orderbooks` は上位N本のスナップショットが定期的に来る型 |
| Coincheck | 素のJSON WebSocket | **必ず「取引所」板。「販売所」は対象外** |

3社にする理由は、2社だと「どちらがおかしいのか」が判定できないから。3社目が中央値の役割を果たす。

> ⚠️ **エンドポイントとチャンネル名は実装時に公式ドキュメントで必ず確認すること。** このコンテナは外部への通信がほぼ塞がれていて検証できていない。ここに書いた仕様は記憶ベースなので、Phase 1 の最初の作業は「3社のAPIドキュメントを開いて、チャンネル名・メッセージ形式・レート制限・利用規約を読む」になる。ここを飛ばすと後の全部が無駄になる。

**販売所を混ぜない**のは特に重要。販売所の価格には数%のスプレッドが最初から乗っていて、それを「歪み」として検出すると全部が嘘の利益になる。板(取引所)同士だけを比較する。

## 3. 記録するデータの形

正規化済みイベントを NDJSON で1行1件。生メッセージをそのまま貯めると3社で1日3GB級になるので、**板は上位50本に切って**記録する(この実験で扱うサイズなら50本で十分深い)。切ったものは戻せないので、これは意識的なトレードオフとして受け入れる。デバッグ用に `--raw` で無加工保存もできるようにしておく。

```jsonc
// 板イベント
{
  "v":  "gmo",            // 取引所ID
  "k":  "snap" | "diff",  // スナップショットか差分か
  "t":  1754500000123,    // ★ ローカル受信時刻(ms)。これが全ての時間軸の基準
  "m":  85231.44,         // performance.now()。単調増加。区間計測用
  "et": 1754500000098,    // 取引所側のタイムスタンプ(無ければ null)
  "b":  [[16523000, 0.052], ...],  // bids [価格, 数量] 降順
  "a":  [[16524500, 0.310], ...]   // asks 昇順
}

// 約定イベント(レイテンシ推定と、板の厚みの裏取りに使う)
{ "v":"gmo", "k":"trade", "t":..., "m":..., "et":..., "p":16523500, "q":0.01, "s":"buy" }

// 接続断・再接続・板リセット。★これが無いと統計が嘘になる
{ "v":"gmo", "k":"gap", "t":..., "reason":"timeout"|"close"|"error", "ms":4210 }
```

`t`(ローカル受信時刻)を時間軸にするのが要点。取引所のクロックは各社ずれているし、そもそも「自分がその情報を知った時刻」でしか自分は行動できない。取引所のタイムスタンプは残すが、判定には使わない。

### ファイル回転

- 1時間ごとに新ファイル、閉じたら gzip
- 圧縮後で 1日あたり数百MB のオーダーを想定
- 起動時に空き容量をチェックし、閾値を切ったら記録を止めて警告(黙って壊れるのが最悪)

## 4. 板の復元(book.mjs)

差分配信の取引所があるので、状態を持つ復元器がいる。

```js
class Book {
  applySnapshot(bids, asks)   // 全置換
  applyDiff(bids, asks)       // 数量0の価格は削除、それ以外は上書き
  best()                      // [bestBid, bestAsk]
  vwap(side, qty)             // → { price, filled, levels } 板を食い潰した平均価格
  isCrossed()                 // bestBid >= bestAsk なら壊れている
}
```

差分配信にシーケンス番号が付かない取引所があるため、取りこぼしを検出できない。対策:

1. **定期強制リスナップ** — N分ごとに再購読してスナップショットを取り直す
2. **クロス検出** — `bestBid >= bestAsk` になったら板が壊れた証拠。即リセットして `gap` を記録
3. **無音ウォッチドッグ** — X秒メッセージが来なければ切断扱い。指数バックオフ+ジッタで再接続

そして最重要:

> **`gap` を含む時間帯は、集計から丸ごと除外する。**

ここを手抜きすると、「片方の板が固まっている間、もう片方が動いた」だけの見かけ上の巨大な歪みが大量に検出されて、結論が全部ひっくり返る。この実験で自分を騙す一番簡単な方法がこれ。

## 5. 実効エッジの定義

ここが設計の本体。

### 前提となる戦略の形

現実的にやれるのは「安いほうで買って、送金して、高いほうで売る」ではない。送金が終わる頃には歪みは消えている。実際にやるのは:

> **両方の取引所にJPYとBTCを置いておき、安いほうで買うのと高いほうで売るのを同時に出す。**

ポジションは中立のまま、その瞬間の価格差だけを取る。在庫の偏りは後でまとめて調整する。この形にすると送金は毎回のコストではなく**定期的なコスト**になる — が、消えるわけではない(§7)。

### 計算

サイズ `q` BTC を、A で買って B で売る場合:

```js
// edge.mjs — 純関数。状態を持たない
function effectiveEdge(bookA, bookB, q, feeA, feeB) {
  const buy  = bookA.vwap('ask', q);   // 買い上がる平均価格
  const sell = bookB.vwap('bid', q);   // 売り下がる平均価格

  // ★ 板が薄くて q を食えなければ、それは機会ではない
  if (buy.filled < q || sell.filled < q) return { valid: false, reason: 'depth' };

  const cost = buy.price  * q * (1 + feeA);   // 手数料込みの支払い
  const rev  = sell.price * q * (1 - feeB);   // 手数料引き後の受取り

  return { valid: true, pnl: rev - cost, bps: 10000 * (rev - cost) / cost };
}
```

素朴な `bestBid_B - bestAsk_A` を使わないのが肝。ベストプライスに 0.001 BTC しか無いのに 0.05 BTC 取れる前提で計算すると、存在しない利益が出る。**必ず板を食い潰した VWAP で計算する。**

手数料 `feeA` / `feeB` は **設定ファイルに手で書く**。取引所の手数料は改定されるし、取引量で変わる階層制のところもある。ここにそれっぽい数字をハードコードすると、その数字が古くなった瞬間に全ての結論が静かに間違いになる。自分で公式の手数料ページを見て `config.json` に書く、という手順を強制する。

```jsonc
{
  "size_btc": 0.01,
  "venues": {
    "bitflyer":  { "taker_fee": null },  // ← 公式手数料ページを見て自分で埋める
    "gmo":       { "taker_fee": null },
    "coincheck": { "taker_fee": null }
  },
  "latencies_ms": [0, 100, 300, 1000],
  "withdrawal_fee_btc": null,
  "batch_size_btc": null
}
```

`null` のまま実行したら**エラーで止める**。デフォルト値を用意しない。

## 6. レイテンシの答え合わせ ← この実験の核心

検出は時刻 `t` の板で行う。しかし現実の約定は `t + Δ` に起きる。Δ には、自分のコードの処理時間・注文の往路・取引所内部のマッチング待ちが全部乗る。個人の環境なら 100〜500ms は普通にかかる。

```js
for (const Δ of config.latencies_ms) {
  // t で「エッジがある」と判定したイベントについて、
  // t+Δ 時点の板で同じ取引をやり直したらいくらになるかを計算する
  const at_t      = effectiveEdge(bookA.at(t),   bookB.at(t),   q, fa, fb);
  const at_tPlusΔ = effectiveEdge(bookA.at(t+Δ), bookB.at(t+Δ), q, fa, fb);
}
```

再生エンジンは全イベントを保持しているので、`t+Δ` の板は正確に再構築できる。これが「後から検算する」設計にした最大の理由。

出力するのは**生存曲線**:

| Δ | 検出数 | 手数料後にプラス | 生存率 | 合計損益 |
|---|---|---|---|---|
| 0ms | ? | ? | ? | ? |
| 100ms | ? | ? | ? | ? |
| 300ms | ? | ? | ? | ? |
| 1000ms | ? | ? | ? | ? |

Δ=0 から Δ=300ms にかけて数字がどう溶けるかを、自分の目で見る。これが Step 2 の成果物そのもの。

**なお `t+Δ` の板で計算した値でも、まだ楽観的な上限。** 板に見えている指値は、あなたの注文が飛んでいる間にキャンセルされうる(逆選択)。実際の約定はこれより必ず悪い。「これでプラスにならないなら絶対に無理」という**否定のための道具**であって、「プラスなら儲かる」証明ではない。

### 経路レイテンシの非対称性(見落としやすい罠)

3社は物理的な距離もネットワーク経路も違う。仮に GMO のデータが bitFlyer より常に 50ms 遅れて届いていると、**存在しない歪みが常時見えてしまう**。片方だけ古い価格を見て比べているから。

対策として、取引所が約定にタイムスタンプを付けている場合、`t - et` の**移動最小値**を片道遅延の下限推定として venue ごとに算出し、レポートに出す。venue 間でこの値が大きくずれていたら、その差を補正した集計も併記する。補正できなくても、**ずれの存在を数字で把握しておく**だけで結論の読み方が変わる。

## 7. 「一過性の歪み」と「恒常的なベーシス」を分ける

取引所Aが取引所Bより常に 0.08% 高い、みたいな状態は普通に起きる(需給・利用者層・入出金の摩擦の違い)。これはゼロを基準に測ると「毎秒エッジがある」ように見えるが、罠がある。

同方向にしか取引が発生しないと、在庫がひたすら片側に寄る。買い続けた側にBTCが溜まり、売り続けた側で枯れる。これを戻すには**送金するしかない**。

送金コストを1取引あたりに割り戻すと、こうなる:

```
1取引あたりの送金コスト(bps) = (出金手数料 / 1回の送金量) × 10000
```

例えば出金手数料 0.0004 BTC、1回に 0.1 BTC まとめて送るなら **40 bps = 0.4%**。裁定の利幅が 0.05〜0.3% の世界で、これは単独で戦略を殺す数字。まとめて送るほど下がるが、その分だけ大きな在庫を寝かせる必要がある(下の資本効率に効く)。

したがって集計では:

1. **恒常ベーシスと乖離を分離する** — 直近30分の移動中央値 `m` を計算し、`乖離 = 現在のベーシス - m` で検出する。ゼロ基準では検出しない
2. **符号の分布を必ず出す** — 儲かる機会の 95% が同じ方向なら、それは裁定ではなく「送金料を払って構造的な価格差を運んでいる」だけ。上の送金コストを引いて再集計する
3. **資本効率で見る** — 両取引所に置きっぱなしの資金が分母。「1取引あたり+150円」ではなく「**投下資本30万円に対して年率何%**」で見る。前者は簡単にそれっぽく見えるが、後者にすると銀行預金以下だった、というのがよくある結末

## 8. レポートの出力

`reports/YYYY-MM-DD.md` と同名の CSV。

- 記録時間、有効時間(gap除外後)、venueごとのイベント数
- venue ごとの片道遅延の推定値と、その非対称性
- 生存曲線の表(§6)
- エッジの継続時間の分布 — 「プラスだった状態が何ms続いたか」の中央値/p90。**ここが自分のΔより短ければ、その時点で終わり**
- 儲かる機会の符号分布と、送金コストを引いた後の再集計(§7)
- 時間帯別の分布(日本時間の朝方・海外時間で全然違うはず)
- **逆張り対照群** — わざと逆方向に取引した場合の損益。エッジが本物なら明確にマイナスになる。ここがゼロ近辺なら、検出しているものはただのノイズか手数料の非対称性

最後の対照群は自分を騙さないために入れる。「なんか勝ってる」の大半はこれで死ぬ。

## 9. 発注コードを構造的に入れないための担保

「あとで発注機能を足す」は事故の入り口なので、足せない構造にしておく。

1. **APIキーを扱う場所を作らない。** 設定スキーマに key/secret のフィールドを持たない
2. **署名処理を書かない。** 取引所の私設APIは HMAC 署名が必須。署名関数が存在しなければ発注は物理的に不可能
3. **検査スクリプトを置く** — `src/` に対して `createHmac` / `api_key` / `secret` / `POST` / `order` を grep して、1件でもあれば非ゼロ終了する `check-no-trading.mjs`
4. 全てのWebSocket接続先は**公開エンドポイントのみ**。認証チャンネルには繋がない

発注が必要になった時は、この実験のデータを見た上で**別のリポジトリに新しく作る**。ここには絶対に足さない。

| 0 | 3社の公式APIドキュメントを読む。チャンネル名・レート制限・利用規約を確認 | 1〜2h |

Phase 5 は最低1週間。相場が荒れた日と凪の日を跨がないと意味がない。1日のデータで判断しない。

## 11. 結果の解釈を先に決めておく

やってから解釈を考えると、都合よく読んでしまう。先に決めておく。

| 結果 | 解釈 | 次の行動 |
|---|---|---|
| Δ=300ms で実効エッジ>0 が **1日0回** | 想定通り。個人のレイテンシでは取れない | **ここで終わる。** データ基盤とスキルが残る。それで十分元は取れている |
| 1日数回、ただし **符号がほぼ一方向** | 裁定ではなく構造ベーシス。送金コストを引くと消える | §7の再集計を確認。ほぼ確実に終了 |
| 1日数十回、**両方向に出る** | 初めて意味がある。ただしまだ「板に見えた指値が実際に取れるか」の壁が残っている | テストネットで約定率を測る段階へ |
| 対照群(逆張り)も同じくらい勝つ | 検出しているのはノイズ。ロジックか計測にバグがある | 実装を疑う |

一番上が出るのが自然な結果だと思っている。それは失敗ではなく、**68ドル→21万ドルの話に対する自分のデータでの回答**が手に入ったということ。

## 12. 実行環境と注意

- **Node 22 以上必須。** グローバル `WebSocket` を使うので依存パッケージはゼロ。Node 20 では動かない
- 記録プロセスは自宅PCかVPSで常時起動。このコンテナは外部通信が塞がれているので**記録は動かせない**。開発とオフライン解析はここでできる
- 各取引所の **API利用規約とレート制限を必ず読む。** 購読の張り直しを短間隔で繰り返すとBAN対象になりうる。再接続のバックオフは最低でも数秒から
- `data/` は `.gitignore`。生の板データをリポジトリに入れない
- 海外取引所(Bybit等)は金融庁の無登録警告対象。この設計に足さない
- 実弾を入れる段階が来たら、その前に **1日の最大損失で止まるキルスイッチを戦略より先に書く**。ただしそれは別リポジトリの話(§9)

## 補足: この設計が答えていないこと

- **マーケットメイク**(指値を置いて手数料をもらう側)は別の戦略で、レイテンシの壁が裁定より低い。国内取引所にはメイカー手数料がマイナス(もらえる)のところもある。この記録基盤はそのまま流用できるので、裁定が死んだ後の次の検証対象としては筋がいい
- **約定率** — 板に見えている指値が実際に取れる確率は、この設計では測れない。テストネットか実弾でしか出ない数字
- **税務** — 全約定をCSVに残す設計は発注段階で必須になる。ここには発注が無いので対象外
