プログラミングを学び始めた頃は、Gitという名前を聞いても「自分にはまだ早い」と感じる方が多いでしょう。簡単なプログラムを一つ書くだけなら、ファイルを保存すれば用は足ります。

ところが、少し大きなものを作り始めると、「前に動いていた状態に戻したい」「どこを変えたか分からなくなった」という場面が出てきます。そのときに役立つのがGitです。この記事では、Gitを学ぶ理由と、最初に押さえたい考え方、基本の流れを整理します。操作を覚えるよりも先に、何のための道具かを理解することを重視します。

## Gitは何のための道具か

Gitは、ファイルの変更履歴を記録して、必要なときに過去の状態へ戻したり、変更の内容を確認したりできるようにする仕組みです。このような仕組みを「バージョン管理」と呼びます。

バージョン管理がない状態では、次のような工夫をすることになりがちです。

- 「main_最終.py」「main_最終_本当に最終.py」のようにファイルを複製して保管する
- 変更前の内容をコメントアウトして残す
- 動いていた状態を思い出しながら手作業で元に戻す

これらは、ファイルが増えて混乱するうえ、どれが最新か分かりにくくなります。Gitを使うと、一つのフォルダの中で、変更のたびに記録を積み重ねられます。ファイルを複製しなくても、過去のどの時点にも戻れる状態をつくれます。

もう一つの大きな役割は、複数人での開発を支えることです。ほかの人と同じプロジェクトを編集するとき、各自の変更をどう合わせるかが問題になります。Gitは、変更を記録し、統合するための仕組みを持っています。ひとりで学んでいる間は実感しにくいかもしれませんが、チームで働く場面では、Gitを使えることが前提とされる職場もあります。必要とされる度合いは職場や職種によって異なるため、希望する分野の求人情報などで確認してみてください。

なお、GitとGitHubは別のものです。Gitは自分のパソコンで動く仕組みで、GitHubのようなサービスは、その記録をインターネット上に置いて共有するための場所です。まずはGitの考え方を理解し、共有は後から加える、という順番で問題ありません。

## 学習の早い段階で触れておくと役立つ理由

Gitを後回しにしてもよいのに、なぜ早めに触れておくことをすすめるのか。理由は三つあります。

一つ目は、失敗しても戻れる安心感が得られることです。初心者は、コードを書き換えるたびに、動かなくなることを恐れがちです。記録を残しておけば、うまくいかなかったときに元に戻せるため、思い切って試せます。エラーが出たときに「動いていた状態に戻して切り分ける」という手順も取りやすくなります。エラーへの向き合い方は[Python学習の始め方｜最初の3ヶ月でやること](/learning/python-gakushuu-hajimekata/)の中でも触れられています。

二つ目は、学習の足跡が残ることです。どんな順番でプログラムを作り上げたのか、どこで修正したのかが履歴として見返せます。学習の記録を別に書く手間が減り、自分の成長を確認する材料にもなります。

三つ目は、成果物を見せやすくなることです。作ったものを他の人に見せたい場面では、履歴の整ったプロジェクトを共有できると、取り組みの過程も伝わります。ポートフォリオを作る段階で慌てて覚えるよりも、日頃から使っておくほうが、流れに慣れやすくなります。

ただし、Gitの習得を目的にしてしまうと、本来の学習が進まなくなります。最初は、ごく基本的な操作だけで十分です。難しい機能を一度に覚えようとしない姿勢が、挫折を防ぎます。

## 最初に覚える言葉と考え方

Gitには独特の用語が出てきます。最初に、次の表の言葉だけ押さえておけば、説明を読むときに迷いにくくなります。

| 用語 | 意味 | たとえ |
|------|------|--------|
| リポジトリ | 変更履歴を含むプロジェクトの保管場所 | 履歴付きのフォルダ |
| コミット | 変更を一区切りとして記録すること | セーブポイントを作る |
| ステージング | 次のコミットに含める変更を選ぶこと | 提出する書類を選んで並べる |
| ブランチ | 履歴を枝分かれさせた作業の流れ | 本編とは別の下書きの流れ |
| マージ | 別の流れの変更を取り込んで合わせること | 下書きを本編に反映する |
| リモート | ネット上など、別の場所にあるリポジトリ | 共有用の保管場所 |

特に大切なのは、「コミット」と「ステージング」の関係です。Gitでは、ファイルを変更しても、すぐに記録されるわけではありません。まず記録に含める変更を選び（ステージング）、そのうえで記録する（コミット）という二段階になっています。この仕組みのおかげで、複数の変更があっても、意味のある単位に分けて記録できます。

コミットには、変更の内容を説明する短いメッセージを付けます。後から見返したときに分かるよう、「何をしたか」を簡潔に書く習慣をつけましょう。「修正」「更新」だけでは、後で何を直したのか分かりません。「ログイン画面の入力チェックを追加」のように、中身が分かる書き方が望ましいです。

ブランチは、慣れてから触れても遅くありません。最初は、一本の流れの中でコミットを重ねる練習だけで十分です。

はじめて試すときは、練習用の空のフォルダを一つ用意し、次のような流れで進めます。

```
git init
git status
git add ファイル名
git commit -m "最初のコミット"
git log
```

それぞれの役割は次のとおりです。

- `git init` — そのフォルダをリポジトリとして使い始める
- `git status` — どのファイルが変更されているかを確認する
- `git add` — 記録に含める変更を選ぶ（ステージング）
- `git commit` — 変更を記録する
- `git log` — これまでの記録を確認する

特に `git status` は、迷ったらいつでも打てる確認用のコマンドです。今どういう状態にあるのかを教えてくれ、次にすべきことのヒントも表示されます。操作が不安なときほど、実行する前後に確認する習慣をつけましょう。

最初は、小さな変更を記録して、履歴を表示するところまで体験できれば十分です。「記録が積み上がっていく」という感覚をつかむことが、最初の目標です。インストールの手順や、初期設定として名前などを登録する方法は、環境によって異なるため、公式の案内で確認してください。

## つまずきやすい点と対処の考え方

Gitは、操作を間違えると取り返しがつかなくなるのではないか、という不安がつきものです。つまずきやすい点と考え方を整理します。

| つまずき | 起きやすい理由 | 対処の考え方 |
|----------|----------------|--------------|
| 何が変更されたか分からない | 確認せずに記録している | 記録前に `git status` で確認する |
| 記録するたびに迷う | 変更をまとめすぎている | 一つの目的ごとに小さく記録する |
| 履歴がぐちゃぐちゃになる | メッセージが曖昧 | 何をしたかを一行で書く |
| 操作を間違えて怖い | 影響範囲が分からない | 練習用のフォルダで試す |
| 英語の表示が読めない | 用語に不慣れ | 表示された内容を検索・翻訳して確認する |

大切なのは、本番のデータで練習しないことです。まず練習用のフォルダで、意図的に変更したり戻したりして、挙動に慣れておきます。失敗しても失うものがない環境で触ると、恐怖心が和らぎます。

また、何かのコマンドを実行する前に、何が起きるのかを説明できるか確認する習慣も重要です。分からないまま、検索で見つけたコマンドをそのまま実行することは避けてください。特に、変更を取り消したり履歴を書き換えたりする種類の操作は、影響が大きい場合があります。分からないときは、ChatGPTやClaudeなどのAIツールに、コマンドが何をするのかを尋ねる方法もあります。ただし、回答は鵜呑みにせず、公式のドキュメントで裏付けを取ってください。

質問する際は、使っているOSやGitの状態、実行したコマンド、表示されたメッセージをそろえると、答えを得やすくなります。この考え方は[学習が続かないのは意志が弱いからじゃない｜続く仕組みの作り方](/learning/gakushuu-tsuzuku-shikumi/)で触れる、学習を止めない工夫とも通じます。

## まとめ

Gitは、ファイルの変更履歴を記録し、過去の状態に戻せるようにする道具です。失敗しても戻れる安心感が得られ、学習の足跡が残り、成果物を共有しやすくなります。

最初に覚えるのは、リポジトリ、コミット、ステージングの三つの言葉と、「編集して、選んで、記録する」という流れです。ブランチなどの発展的な機能は、慣れてから取り入れれば十分です。まずは練習用のフォルダで、小さな変更を記録して履歴を眺めるところから始めてみてください。
